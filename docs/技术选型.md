## 1. 选型原则

1. **先验证玩法，后堆框架**：核心是 60fps 状态机 + 按住判定，不是营销站或后台。
2. **包体与首屏**：点开即玩；依赖越少越好。
3. **表现与规则分离**：与模块设计一致；换 Skin 不换引擎。
4. **Skill 分工**：
   - `frontend-design` → HUD / 标题 / 结算壳的视觉决策（题材驱动、反模板）
   - `design-taste-frontend` → 若做落地页、宣传页、或需浏览器 inspect 打磨 UI 壳时启用；**游戏 Canvas 内玩法不走 draw/inspect 全流程**

---

## 2. 结论一览（MVP）

| 层级 | 选型 | 不选 / 暂缓 | 理由 |
| --- | --- | --- | --- |
| 语言 | **TypeScript** | 纯 JS | 状态机与配置类型清晰，改手感不易踩坑 |
| 构建 | **Vite** | Webpack / 无构建长期硬撑 | 秒级 HMR、静态部署简单 |
| UI 框架 | **无（Vanilla）** | React / Vue / Svelte | 无组件树收益；rAF 循环更直接 |
| 游戏渲染 | **Canvas 2D** | WebGL / Three.js | 2D 表情与场景足够；调试成本低 |
| 游戏引擎 | **自研薄层**（按模块设计） | Phaser / Pixi（MVP） | 状态机已定制；避免引擎心智税 |
| HUD / 壳 | **HTML + CSS Variables** | Tailwind（MVP） | 字少、层少；token 好配合 frontend-design |
| 动画（壳） | **CSS + 少量 Web Animations** | GSAP（MVP） | 惊吓可用 CSS；落地页再按 Taste 上 GSAP |
| 音频 | **Web Audio API**（或包装一层） | Howler（可后补） | 解锁策略自控；依赖少 |
| 存储 | **localStorage** | 后端 / IndexedDB | 仅最高分与静音 |
| 部署 | **静态托管**（GitHub Pages / 任意静态） | Node 服务 | 纯前端 |

**一句话**：`Vite + TypeScript + Canvas 2D + HTML/CSS HUD`。

---

## 3. 与 Skill 的适配说明

### 3.1 Anthropic `frontend-design`

适用于：BOOT 标题屏、RESULT 结算、静音按钮、分数 HUD、手势引导。

要求落地时：

- 先写 **4–6 色 token + 字体角色 + 一句视觉原则**，再写 CSS
- 题材锚点：偷冰箱 / 熟睡黄龙 / 惊吓反差（萌 → 炸），禁止套用通用 SaaS 紫渐变、三卡片模板
- 动效：惊吓做「一个主时刻」；不要每层 fade-up

### 3.2 Taste `design-taste-frontend`

| 场景 | 是否跑完整 Taste run |
| --- | --- |
| 游戏本体（Canvas 循环） | 否；只借鉴 anti-slop 与题材库存思维 |
| 对外宣传落地页 / 作品集页 | **是**；`draw.mjs` → 构建 → `inspect.mjs` |
| 仅打磨 HUD 壳 | 可选；轻量用 frontend-design 即可 |

环境：Node 22+（本机已满足）、Chrome/Edge；工作目录产物建议进 `.taste-skill/`（gitignore）。

## 5. 后续可升级路径（非 MVP）

| 触发条件 | 升级 |
| --- | --- |
| 粒子/多层精灵性能不够 | 引入 PixiJS，保留自研状态机 |
| 多关卡编辑器 | 再评估 Phaser Scene |
| 宣传站要奖级观感 | 启用 Taste 完整 run |
| 需要组件化复杂菜单 | 局部引入 Preact（仍避免整站 React） |

---

## 6. 明确拒绝（本期）

- Next.js / SSR（无 SEO 刚需）
- 状态管理库（Redux 等）——一局状态用 `GameSnapshot` 足够
- UI 组件库（shadcn 等）——字少，库会反向模板化
- 后端与账号
